# Product Requirements Document
# Amusement Park Simulation Website

---

## 1. Project Overview

A web application that simulates the daily operations of an amusement park over a user-defined number of days. The user inputs the number of days to simulate, clicks a button, and receives a fully generated analytical report with data visualizations and a downloadable PDF summary. Every run is completely random — no data is persisted between runs and no database is used.

---

## 2. Tech Stack

| Layer | Technology |
|---|---|
| Frontend | React (Vite) |
| Backend | Python, FastAPI |
| Data processing | Pure Python (in-memory, no database) |
| PDF generation | WeasyPrint or ReportLab |
| Deployment | Railway (or equivalent) |

**Critical constraint: No database.** The simulation runs entirely in memory on the backend. Once the response is returned to the frontend, all simulation data is discarded. Every run starts fresh.

---

## 3. User Flow

1. User lands on the website and sees the simulation configuration screen
2. User enters a number of days to simulate (suggested range: 1–365)
3. User clicks the **"Run Simulation"** button
4. A loading/progress indicator is shown while the backend processes
5. The report renders in-browser showing all analytics and visualizations
6. User can download the full report as a PDF

---

## 6. The 7 Rides

Each ride has the following attributes baked in as constants:

| Ride Name | Category | Thrill Level | Max Hourly Capacity | Avg Ride Duration (min) | Breakdown Probability |
|---|---|---|---|---|---|
| Thunderbolt | Roller Coaster | High | 800 | 3 | 0.05 |
| Aqua Rush | Water Ride | Medium | 600 | 5 | 0.03 |
| Free Fall Tower | Drop Tower | High | 300 | 2 | 0.04 |
| Carousel | Family | Low | 1200 | 4 | 0.01 |
| Bumper Cars | Family | Low | 700 | 6 | 0.02 |
| Haunted Mansion | Dark Ride | Medium | 900 | 8 | 0.02 |
| Mini Coaster | Kids Only | Low | 1000 | 3 | 0.01 |

**Breakdown logic:** Each day, each ride rolls against its breakdown probability. If it breaks down, it is closed for a random number of hours (1–4) that day, reducing its throughput proportionally. Breakdowns are logged as incidents in the report.

**Aqua Rush weather dependency:** On rainy days, Aqua Rush is closed entirely. On sunny days, its demand multiplier is 1.5x.

## 8. Visitor Archetypes

Each simulated day, visitor groups are generated by sampling from these archetypes using weighted probabilities. The archetype determines group size, ticket mix, ride preferences, spending behavior, arrival time, and hours spent in the park.

### Archetype 1: Family with Young Kids
```

group_size: 3 to 6 people
ticket_mix: ~2 adults, ~2 children, ~1 toddler
ride_preferences: Carousel, Mini Coaster, Bumper Cars, Haunted Mansion
ride_aversions: Thunderbolt, Free Fall Tower
food_spend_multiplier: 1.8
merch_spend_multiplier: 1.5
hours_in_park: 6 to 9
arrival_window: 9am to 12pm
```

weight: 0.15
group_size: 2 to 3 people

food_spend_multiplier: 0.7

## 9. Weather System

Each simulated day is assigned a weather state by weighted random roll.

| Weather State | Daily Probability | Attendance Multiplier | Notes |
|---|---|---|---|
| Sunny | 0.50 | 1.2x | Aqua Rush demand +50% |
| Cloudy | 0.30 | 1.0x | Baseline, no modifiers |
| Rainy | 0.20 | 0.5x | Aqua Rush closed, food spend +20% (shelter behavior) |

---

## 10. Daily Attendance Model

Base daily attendance is determined by:

1. **Base attendance:** random integer between 2,000 and 5,000 visitors
2. **Weather multiplier:** applied from the weather state
3. **Day of week multiplier:** weekends are 1.4x, weekdays are 1.0x
4. **Random variance:** ±10% noise applied on top

The simulation tracks which day of the week each simulated day falls on (starting Day 1 as a Monday).

---

## 11. Revenue Model

### Ticket Revenue
Calculated from the ticket mix of each visitor group based on archetype. Toddlers are free.

### Ride Revenue
Rides are included in the ticket price — they do not generate separate revenue. They contribute to visitor satisfaction and queue analytics only.

### Store / Restaurant Revenue
Each visitor group visits a random number of stores during their time in the park (influenced by archetype spend multipliers). Transaction values are sampled from a normal distribution centered on each store's avg transaction value with ±20% variance.

### Total Daily Revenue
```
daily_revenue = ticket_revenue + food_beverage_revenue + retail_merchandise_revenue
```

---

## 12. Simulation Logic (Per Day)

Each simulated day executes the following steps in order:

1. Roll weather state
2. Determine day of week
3. Calculate total attendance for the day
4. Generate visitor groups by sampling archetypes (weighted, school group weekday-only rule applied)
5. For each ride, roll breakdown probability — log incident if breakdown occurs
6. For each visitor group, simulate behavior:
   - Assign ticket purchases based on archetype ticket mix
   - Assign ride visits based on preferences, availability (not broken down), and hours in park
   - Assign store visits based on archetype spend multipliers
7. Aggregate all transactions into daily totals
8. Log the day's results

## 13. Report — Analytics Sections

The report rendered on the frontend (and exported as PDF) must include the following sections:

### Section 1: Executive Summary
- Total simulation period (e.g., "30-day simulation")
- Total attendance across all days
- Total revenue across all days
- Best single day (date + revenue)
- Worst single day (date + revenue)
- Most popular ride
- Top grossing store

### Section 2: Daily Attendance & Revenue Trends
- Line chart: daily attendance over the simulation period
- Line chart: daily total revenue over the simulation period
- Weather state color-coded on both charts (sunny = yellow, cloudy = gray, rainy = blue)

### Section 3: Revenue Breakdown
- Pie chart or donut chart: ticket revenue vs. food & beverage revenue vs. retail revenue as % of total
- Bar chart: revenue by day of week (averaged across all occurrences)

### Section 4: Ride Analytics
- Bar chart: total riders per ride across the simulation
- Bar chart: average queue utilization per ride (riders as % of max capacity)
- Table: ride breakdown incidents log (which ride, which day, hours down)

### Section 5: Store & Restaurant Analytics
- Bar chart: total revenue per store/restaurant ranked highest to lowest
- Grouped bar chart: food & beverage revenue vs. retail revenue per day

### Section 6: Visitor Demographics
- Stacked bar chart or pie chart: archetype distribution across total visitors
- Line or bar chart: average spend per visitor per day
- Table: ticket type breakdown (how many adult, child, toddler, senior tickets sold total)

### Section 7: Weather Impact
- Summary table: avg attendance and avg revenue on sunny vs. cloudy vs. rainy days
- Count of sunny, cloudy, and rainy days in the simulation period

### Section 8: Incidents Log
- Table of all incidents that occurred (ride breakdowns, etc.) with day number, ride name, and hours affected

## 14. PDF Export

The PDF should include all sections from the report in a clean, printable format. Charts should be rendered as images in the PDF. The PDF download is triggered by a button in the frontend report view.

## 16. Build Order Recommendation for Claude Code

Build in this sequence to avoid blocking dependencies:

1. **Backend constants** — archetypes.py, rides.py, stores.py (no logic, just data)
2. **Simulation engine** — weather, attendance, daily loop, aggregation
3. **FastAPI endpoint** — wire engine to POST /simulate, verify JSON output
4. **PDF generator** — takes engine output, produces downloadable PDF
5. **Frontend config screen** — day input, run button, calls API
6. **Frontend report screen** — renders all charts and tables from API response
7. **PDF download button** — wire frontend download to backend PDF endpoint

---

## 17. Notes & Constraints

- The simulation must complete in under 60 seconds for any input up to 365 days
- All randomness should use Python's `random` module with no fixed seed (true randomness per run)
- The frontend should handle loading state gracefully — show a spinner or progress message while waiting for the backend
- Charts should be built using Recharts (already available in the React environment)
- The backend should include CORS middleware so the frontend can call it during local development
- No Emojis in the code
